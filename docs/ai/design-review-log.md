# Design review log

How the design was reviewed before any code was written, which AI mistakes the review caught, which critiques were kept or rejected, and which claims were turned into experiments instead of being trusted.

The decisions themselves are in the [decision ledger](decision-ledger.md) (`D1`–`D76`); the final design is in the [ADRs](../adr/). This log records the *path* to them. It is curated: no raw transcripts.

> **Status:** first draft, written at the end of the design phase while both sides of the review were still available. P7 completes section 4 from the raw review material and adds the implementation-phase entries (section 6).

## 1. How the review ran

| Step | Who | Output |
|---|---|---|
| Design discussion | The author with a Claude model as design partner | Ten ADRs, `architecture.md`, `future-work.md` |
| Checklist | Reviewer (Claude Fable 5.2), Turn 0 | Every requirement of the assessment as an ID (R1–R36), with interpretations |
| Adversarial review | Reviewer, Turns 1–12, one document per turn | Findings (`F`), proposals (`P`), notes (`N`); each claim labelled *Verified*, *Reasoned* or *Unverified*; rejected alternatives steelmanned; at most three improvement proposals per document |
| Final report | Reviewer | Cross-document findings, the fallback principle, the day plan |
| Triage | Author with the design partner | Each finding accepted, revised or rejected, recorded in the ledger with its source (`T2 F1` = Turn 2, finding 1) |
| Ledger reviews (two) | Reviewer | Inconsistencies inside the ledger itself |
| Preparation session | Implementation agent | ADRs revised to the ledger; plan, `CLAUDE.md`, progress log; ten open questions settled (D62–D73) |

The review prompt asked for judgement, not agreement: the reviewer had to say when a document was wrong, when a fix was disproportionate, and which of its own claims it had not verified. The sanitised prompt is added to this folder in P7.

## 2. Mistakes in the design that the review caught

The design partner produced every item below with confidence. None was caught by the partner itself. The turn and finding references were checked against the raw review material.

| # | Mistake | Consequence if shipped | Caught in | Fix |
|---|---|---|---|---|
| 1 | **Claim guard accepted only `status = 'queued'`.** The relay publishes before its transaction commits, so a fast worker sees `pending`, claims nothing and acks. | The message is dropped. During triage, the partner first estimated the impact as a five-minute delay until the stale sweeper runs; that estimate was also wrong, because the sweeper's progress signal was tied to claims, so on an idle lane the row stayed `queued` indefinitely. The review's only blocker. | T2 F1, T4 F1 | D1, D10: widened guard; the relay's row locks across the publish are now part of the design |
| 2 | Stale-queued sweeper conditions | Failed in both directions: missed stuck rows on idle lanes, republished healthy rows under load | T3 F1, F2 | D5: reconciliation on every reconnection, `requeue-stale`, oldest-queued-age alert |
| 3 | Outdated RabbitMQ and Kafka facts: quorum queues with two priority levels, Kafka without per-message nack, RabbitMQ without per-message delay, memory pressure as an argument for quorum queues | The broker choice and its rejected alternatives were argued from facts that were no longer true | T1 F2, F8, F9; T2 F5; T3 F4 | D7, D48; ADR-0001 alternatives rewritten |

## 3. Mistakes in the review process

- **Proposal reversed after objection.** For cancel after an attempt with outcome `unknown`, the author's first answer, drafted with the design partner, was `409`. The reviewer objected that the client cannot act on it; the final rule allows the cancel and returns `may_have_been_sent: true` (D15, T7, revised).
- **A ledger decision replaced in the ledger review.** The first version of D8 handled long open circuits with cancel-and-resubscribe; the ledger review replaced it with a 24-hour `x-consumer-timeout`, kept as a fallback in E6.
- **Plan reconstructed instead of read.** The reviewer's final report was not among the preparation session's inputs, so the session reconstructed the plan from the ledger. A comparison with the real report found differences in the fallback order and in what is never dropped; they were corrected before merge (D73).
- **The reviewer's own miscount.** At Turn 0 the reviewer counted 12 containers from the overview, while ADR-0005 stated 15. The documents were consistent; the count was the reviewer's mistake.
- **Ledger reviews found contradictions inside the ledger** (trace rule, transition 12 preconditions, the api's required dependencies), each now resolved (D13, D14, D39).

## 4. Choices questioned and kept

| Choice questioned | Decision | Reason |
|---|---|---|
| Default TTLs (high 10 min, normal 6 h, low 24 h) | Kept (D31, T7 F10) | The TTL bounds the largest burst each priority can absorb; the README states that bound |
| One `notifications` table | Kept; rationale replaced (D21, T4 F4) | Write volume at 294 msg/s is negligible; splitting hot columns is future work |
| The 1 s back-off floor | Kept (D68, preparation session) | Full jitter can produce near-zero delays; the floor protects the provider |
| Dead-letter queues after the custom delivery limit was removed | Kept as a safety net (D6) | The real defence is the failure budget, but a poison queue makes a broker-side failure visible |
| End-to-end latency measured from `COALESCE(scheduled_at, created_at)`, not from `due_at` | Kept; the reviewer attacked it in Turn 9 and could not break it | `due_at` is overwritten on every retry, so a message retried for hours would look instant; `created_at` alone would make scheduled notifications look late (ADR-0009 §1) |

| Critique or proposal | Outcome | Reason |
|---|---|---|
| Repair the stale-queued sweeper with a worker heartbeat and a "healthy since" window (the reviewer's own fix for T3 F1 and F2) | Not adopted; the sweeper was replaced by reconciliation on reconnection (D5) | Compared side by side, reconciliation is simpler, deterministic and easier to test; the reviewer agreed |
| Cut transition 12, the late-success rescue (T4 P1) | Withdrawn by the reviewer in Turn 6; kept (D14) | Once the cut criterion became whether correctness can be shown by tests, two deterministic tests were enough |

## 6. Implementation phase

*Added from P0 onwards: experiment results, AI mistakes caught in code review or by `make verify-suite`, and any decision changed by evidence.*

| Phase | What was assumed | What the evidence showed | What changed |
|---|---|---|---|
| P1 | The plan and ADR-0010 named two tests that "would have caught the dropped-message defect" (a claim guard of `status = 'queued'` only): the store-level wait-for-commit test and the end-to-end test of a single notification on an idle system. The closing mutation check of P1 was to show both failing. | With the guard narrowed, the store-level test failed every time, and the idle end-to-end test **did not fail once in 220 runs**. With one message on an idle system the relay commits about 1 ms after its publish returns, and the worker's claim (delivery, a Redis reservation, then the claim) arrives later, so the narrowed guard still finds a `queued` row. Which side wins depends on the machine: the test could not be relied on to catch the defect. | A forced-race test, `TestE2E_WorkerFasterThanRelayCommit`, holds the relay's transaction open until the worker's claim is seen waiting on the row lock, through the real broker; it fails every time under the mutation and replaced the idle test as the mutation target. The idle test stays as the plain proof that one notification is sent. ADR-0010, the plan and D54 were corrected. The claim about what a test catches was only settled by removing the guarantee and running it. |
| P2 | ADR-0006 §6 specified the batch insert as one `INSERT … SELECT FROM unnest(…) ON CONFLICT … DO NOTHING` and discussed conflicts only against rows that already exist. Twelve review turns and two ledger reviews did not ask what two batches do to each other while both are still open. | Two concurrent batches with the same `dedupe_key` values in opposite orders **deadlocked in 3 of 3 runs** (`40P01`): each insert waits on the other transaction's uncommitted entry in the unique index. The scenario is the one `dedupe_key` exists for, a campaign batch that is re-split and resubmitted. **It was found by the concurrency test written with the store layer, not by review.** | The batch insert orders its rows by `dedupe_key`, so every batch takes its index entries in one global order; `TestCreateBatch_ConcurrentOverlappingKeysNoDeadlock` fails without the `ORDER BY` and passes with it. ADR-0006 §6 states the rule. |
| P2 | D34 and ADR-0006 §8: two `sqlc` queries, with and without the status filter, are each "served in order by its index", and an `EXPLAIN` check tied to a test guards it. The design assumed that the plan seen in `EXPLAIN` is the plan that runs. | The check was run under both plan modes. With a **generic plan** (what a prepared statement switches to after a few executions) the status query was a bitmap scan of every row of the status followed by a sort: the optional filters (`$n IS NULL OR col = $n`) leave the planner with an estimate of one row, so the sort looks free. With a custom plan the same text is an ordered index scan with the keyset as index condition. An `EXPLAIN` with literal values would have passed while production sorted. | Both listing statements always run with a custom plan (the unnamed statement), the `EXPLAIN` test asserts the custom plans for a frequent and a rare status and logs the generic plan as the reason, and `TestList_RunsWithCustomPlans` checks that the listing never enters the prepared-statement cache. ADR-0006 §8 states the rule. Found by the test, not by review. |
| P2 | ADR-0006 §7: a batch cancel is "a single `UPDATE ... WHERE batch_id = $1 AND status IN (...)`". The previous session noted that two cancels of one batch could deadlock in principle and had not reproduced it. | The author asked for a fixed lock order and for an attempt to break the unordered statement. While both sessions met the rows in the same order it **never deadlocked** (720 rounds of two cancels over 1,000 rows: the same plan with and without rows moved by updates, and different plans over rows in their original places, with and without single claims and cancels alongside): every plan then locks in physical order. It deadlocked (`40P01`) **only when the two sessions were forced to scan in different orders**: one sequential scan, one index scan, over rows that HOT updates had moved inside their pages (43 deadlocks in 600 rounds; 20 of 20 test runs failed). Neither condition alone was enough. | The statement now locks the cancellable rows `ORDER BY id FOR UPDATE` and then updates them, in one statement; it passed every setting above without a deadlock, and `TestCancelBatch_ConcurrentSameBatch` keeps the forced-order case. In production the two sessions would need different plans for the same statement, which is rare but not excluded (a plan can change between two executions), so the order is fixed rather than assumed. |
| P2 | The listing cursor is "an opaque, base64-encoded `(created_at, id)`" and its decoder rejected everything that is not exactly that; the table test of the decoder passed. | The fuzz target added in the same phase, with the property "a cursor that decodes encodes back to the same string", failed in about two seconds: Go's base64 decoder skips carriage returns and line feeds, so a string with one inside decoded to a valid cursor. Harmless for the query, but one cursor had several spellings. | The decoder accepts a cursor only if encoding it again gives the input; the fuzzer's input is a seed and a regression test. Found by the fuzz test, not by review. |
| P3 | D12 and D78 give the expiry pass and the idempotency-key cleanup as bounded batches "selected with `FOR UPDATE SKIP LOCKED`", each served by its index on `expires_at`. The first measurement of the statements (statistics taken with the backlog already expired) agreed: an ordered index scan, then a look-up of each row by primary key, 4 to 16 ms per batch of 1,000. | The delegate's first `EXPLAIN` showed a different plan, so the main loop asked for the plan **that runs**, in the order production meets it: statistics taken while nothing is expired, then 30 passes that find nothing (a pass runs every second, the cleanup every minute), then 200,000 rows expiring at once, as after an outage. Postgres had by then cached a **generic plan** built for one or two rows. For the cleanup it was a nested loop of every expired key against the batch (200,000 × 1,000 comparisons): **11 to 13 s per delete of 1,000 keys**, holding its row locks, until autovacuum happened to analyse the table. The expiry statement scanned the whole expired backlog on every batch (53 ms falling to 9 ms; total work quadratic in the backlog). The same class of problem as the listing's, with a different trigger: the selectivity of `expires_at <= now()` changes with time while the cached plan does not. A rewrite of the join inside the statement was measured and was worse. | Both statements run as the unnamed statement, planned with their values on every call, like the listing (`customPlanDB`); `TestExpiry_RunsWithCustomPlans` fails when either is a cached statement. Measured after the change: 200,000 rows expired in 1.9 s, 200,000 keys deleted in 0.5 s, no slow batch. Found by measuring the production sequence, not by review and not by the first `EXPLAIN`. |
| P3 | After the listing and the expiry pass, the remaining statements of the hot path (the relay's count, lane selection and `queued` update, the claim, the worker's final writes, the lease sweeper's statements: eleven in all) were assumed to be safe as cached prepared statements, because each is a primary-key look-up or an ordered scan of an index made for it. Nobody had measured it. | The author asked for a systematic check after the third defect of this class. On 1,000,000 pending rows and on 200,000 expired leases, with fresh statistics, **the forced generic plan and the custom plan are identical for all eleven**: the assumption held, now with numbers ([ADR-0003](../adr/0003-bounded-relay-buffer-and-sweepers.md) §6). The same harness, run in the order production can meet (statistics from a 40-row table, 35 executions, then the backlog without an `ANALYZE`), found something the question had not asked for: **every cached plan was still the sequential scan that was right for 40 rows.** One primary-key write took 90 to 480 ms, a relay tick about 6 s, a sweep of 500 leases 42 to 48 s, until autovacuum's `ANALYZE` invalidated the plans (22 s later in the run measured; bounded by the launcher's 60 s cycle). The foreign-key check inside the claim's insert has the same stale plan and is out of the application's reach. Three remedies were measured (the unnamed statement for all eleven: +0.54 ms per message, does not reach the foreign-key check; `plan_cache_mode = force_custom_plan` on the connection: +0.10 ms per message, reaches the foreign-key checks, not the one statement without parameters; doing nothing). | Nothing in the code: the eleven statements stay cached, as the comparison says. The stale-plan window is an open issue for the author with the measurements and a recommendation, not a change made on the side. **Found by measurement after the expiry defect, not by review;** the second finding came from running the statements in production order instead of only explaining them. |
| P3 | D79: with `plan_cache_mode = force_custom_plan` on every pool, the stale-plan window after a burst is closed (measured in a scratch copy: a relay tick 122 ms instead of 6 s, a claim with its final write 1 ms instead of 300 ms). The author asked for the measurement to be repeated on the real code. | On the real code the harness confirmed it (relay tick 32 to 36 ms, claim 1.0 to 1.4 ms, the foreign-key check 0.003 ms instead of up to 87 ms, `generic_plans = 0` for every statement). **The same burst on the Compose stack did not get faster:** about 35 messages per second per channel with D79 against about 32 without. With `auto_explain` the reason was 6,624 claims in the minute at about 290 ms each: a **custom** plan that looks the row up through the partial expiry index. The statistics had been taken while the outbox was empty, the normal idle state, and call that index empty; the harness had not shown it because its warm-up left a few pending rows in the statistics. With tables that were never analysed, D79 delivered the full 98 per second from the first second. | D79 stays (it removes the cached-plan class). The limitation is stated in ADR-0003 §6 and `future-work.md` with the numbers, and the remedy at the level of statistics is an open issue for the author (it was already planned for P6 for two other statements; the claim now belongs to the same class). **Found by repeating the measurement on the deployed stack, not by the harness and not by review:** the harness measured what the hypothesis predicted, the stack measured what happens. |
| P3 | Reconciliation as one statement, "all `queued` rows return to `pending`" (D5, ADR-0003 §3), run by a goroutine of the relay on every (re)connection. | Line-by-line review of the statement by the delegate that wrote it and by the main loop: it reconciles the rows that are `queued` **in its snapshot**. A lane transaction that publishes on the old connection and commits `queued` just after the statement started is missed, and its row stays `queued` with no copy in the broker until the age alert, `requeue-stale` or expiry. Separately, the first version without a lock order deadlocked with the batch cancel in the first round of its test (`40P01`). | Reconciliation runs in the publishing loop's own goroutine, between two cycles, never while a lane transaction is open (`TestReconcile_NeverOverlapsALaneTransaction`); the rows are locked in `id` order, like the batch cancel (`TestReconcile_VersusBatchCancel`). The first by review of the statement against the loop that would call it, the second by its concurrency test. |
| P3 | D76 and ADR-0005: each delivery carries "the connection epoch", a counter that advances when the connection is lost; P0 had recorded that the state notification and the deliveries arrive on different Go channels and that the implementation must not depend on which is read first. | Reading `amqp091-go` v1.17.0: its state notification is asynchronous, so a counter advanced from it can lag behind the recovered channel, and the library's own topology recovery resubscribes a consumer under its old tag on the same Go channel, so a delivery cannot be attributed to a session by when it is read. What runs synchronously inside the recovery, before the channel is reset, is the dial function and the channel-close hook. | The epoch advances in those two hooks; every subscription gets a tag and an epoch of its own, and the library's topology recovery is replaced by an explicit one; the check and the ack are one critical section. `TestWorker_ConnectionLossWithBufferedMessages` asserts it on the wire, and with the check removed the broker closes the channel with `406 unknown delivery tag`. Two narrow windows that the library gives no hook to close are documented, not hidden. |
| P3 | `Connection.IsOpen()`: "true only when the connection is open and the topology has been declared on it", implemented as the generation check under the connection's lock followed by the library's closed flag. The line-by-line review of the epoch work went to the answer path and the recovery hooks; `IsOpen` was read as two independent conditions. | After the merge the `integration` job on `main` was red once: the test that samples `IsOpen` across a reconnection saw it true before the topology existed. It did not reproduce locally in 40 runs. Reading the two reads against the library's reconnect loop gave the cause: an attempt that starts between them (its dial hook, then the library clearing its flag) makes the old generation meet the new connection's cleared flag. A deterministic test that places the attempt at the read of the flag failed on the merged code at once. In the relay the wrong answer only starts a lane that the publisher's own check then refuses. | The reads are swapped (the library's flag first, the generation second), with the argument in the doc comment; `TestIsOpen_ReconnectionAttemptBetweenItsTwoReads` guards it. **Found by the CI runner's scheduling, not by review and not by the local runs;** a check built from two reads of state that one event changes in sequence needs its order argued like a lock order. |
| P4 | ADR-0008 §2 and D40, after the design review had already closed two gaps of a node-type allow-list (builtin functions, `define`): "after parsing, the template set must contain exactly one template, otherwise the source is rejected", and the walker walks "the parsed tree". | Before any code, a probe of the parser on Go 1.27: a `define` named like the source itself leaves **one** template in the set, the definition, in place of the tree the parser returned for the top level. The count passes, and a walker that reads the returned tree sees an empty template. A second probe: `html/template` rewrites a tree on first execution, so "the parsed tree" is not one stable object. The fuzz target then found the mirror case in three seconds (an *empty* definition of the same name is dropped by the parser and cannot be seen at all; harmless). The first mutation check showed a second thing: with the function-name check deleted, a builtin was still refused, by the argument check, which names the two functions as well. | The rule is "the set holds exactly the tree the parser returned", the walked tree object is the one handed to the engine, and one constructor is the only way to a renderable template. The tests assert the reason of a rejection, not only the rejection, so each of the two mutations fails a named test; a third mutation in which a builtin is really accepted is reported next to them. **Found by probing the library before specifying, not by the review of the design;** a rule about a library's data structure needs the structure looked at. |

## 7. What this shows about using AI here

- The partner's mistakes were not random: most were confident statements of outdated or unchecked facts (rows 3, 6, 7, 10) and races between two actors (rows 1, 2, 13). The test matrix is organised by actor pairs for this reason (D49).
- A second model with an explicit mandate to disagree found the blocker; agreement was never the goal.
- Unverified facts were converted into experiments and tests rather than settled by argument.
- `make verify-suite` (D54) applies the same idea to the code: removing a guarantee must make a named test fail.
