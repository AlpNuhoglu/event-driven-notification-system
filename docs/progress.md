- **Decisions taken** (within the latitude of the ledger and the ADRs; the ADRs are updated):
  1. **The rules of `scheduled_at` and `expires_at` are judged by the API's clock, read once per request** (every item of a batch at the same instant); no database round trip. Times are compared as they are stored, cut to the microsecond. The database's clock still decides when a row is due.
  2. Codes: `in_the_past` (older than the tolerance), `too_far_ahead` (beyond the horizon), `too_soon` for an `expires_at` on create (the code of redrive). The tolerance and the horizon include their limits.
  3. **`"scheduled_at": null` means absent** (the request example of ADR-0006 §3 sends it); `"expires_at": null` is `invalid_type`, like every member the example does not show as `null`.
  4. The `expires_at` rule counts from the `scheduled_at` when that is in the future, otherwise from now (also for a `scheduled_at` inside the tolerance). When `scheduled_at` is invalid, `expires_at` is checked for type and format only.
  5. **A request that fails only the clock rules is answered from its `Idempotency-Key` when it is a retry** (above). ADR-0006 §11 and ADR-0008 say so.
  6. **The variables that existed are used:** `SCHEDULE_PAST_TOLERANCE` and `SCHEDULE_MAX_HORIZON` had been in the configuration and `.env.example` since P0, read by nothing. The brief named new ones and the delegate renamed the old; the main loop restored the old names.
  7. Times are read as redrive reads its `expires_at` (`time.RFC3339`), with what that parser accepts.
  8. **The list is in ASCII order** (`COLLATE "C"` in the comparison and the order, with an index of that collation), so the order and the walk do not depend on the database's default collation. The cursor is the base64url form of the last name, with one accepted spelling; an empty cursor is `invalid_parameter`. Inactive templates are listed.
  9. With D40 as amended, only an empty value is false: the string `"false"` is not empty and takes the `if` branch, like the number `0`.

  1. **The one-template rule is "the set holds exactly the tree the parser returned"**, which is stronger than the count D40 and ADR-0008 name and rejects the self-named `define`.
  2. **The source is parsed without a function check** and the walker alone decides about function names; the walked tree object is the one handed to the engine; `CompileTemplate` is the only constructor and runs on every use, also on a stored body.

### 2026-11-19 — P3: the red `integration` job on `main` (follow-up)

- **Reported by the author:** after the merge of `p3/recovery` the CI run on `main` (commit 520e85a) was red in the `integration` job; the other six jobs passed.
- **What failed:** one test, `TestConnection_TopologyDeclaredAgainOnEmptyBroker` (`internal/queue`), with four lines: "IsOpen was true before the topology existed on the recovered connection", "no reconnection signalled", "opens 1 after one reconnection, want 2", and "publish after the wipe: publish batch: connection not open". The same test had passed on the pull request's own run and passes locally (40 of 40, also with two CPUs).
- **Cause: a race in `Connection.IsOpen()`, not in the test.** `IsOpen` combined two facts read at two moments: our generation ("the topology is declared on the current connection", under the connection's lock) and then the client library's closed flag. A reconnection attempt changes both, in this order: its dial hook starts a new generation, then the library clears its closed flag, and only later is the topology declared. An attempt that began **between** the two reads made `IsOpen` see the old generation, still usable, and then the cleared flag of the new connection, and answer true before the topology was declared. The test samples `IsOpen` in a tight loop across the reconnection, which is how the CI runner hit a window of a few microseconds. All four lines follow from that one wrong answer: the test took it for the reconnection and went on while the recovery was still running.
- **Effect outside the test:** the relay asks `IsOpen` before every lane. A wrong true starts a lane transaction during a reconnection; the publisher's own check (the `lost` signal, which is set and cleared inside the recovery and has no such gap) then refuses the batch, the lane is rolled back and logged as failed. Nothing is published or recorded wrongly. This is very likely the single unexplained "lane failed" line of the wipe scenario noted in the previous entry.
- **Fix:** `IsOpen` reads the library's flag first and the generation second. If the flag is read as cleared because an attempt cleared it, that attempt's dial hook has already run, so the generation read afterwards is the attempt's, and it counts as usable only once the topology is declared on it. The doc comment of `IsOpen` states the argument.
- **Test:** `TestIsOpen_ReconnectionAttemptBetweenItsTwoReads` places a reconnection attempt exactly at the read of the flag (the flag is read through a field so that a test can do this). **It fails on the code before the fix** with "IsOpen is true during a reconnection attempt, before the topology is declared on the new connection" and passes after it. `TestIsOpen` covers the plain cases, including a failed attempt that leaves the library's flag cleared.
- **Pull requests opened:** [#13](https://github.com/AlpNuhoglu/event-driven-notification-system/pull/13) from `p3/isopen-race`.
- **Checks:** `make test` green (21 packages); the originally failing test 40 of 40 with two CPUs; `make lint` 0 issues. `gh pr checks` is reported on the pull request.
- **Not verified:** the failure itself could not be reproduced locally by repetition before the fix; the diagnosis rests on the code path and on the deterministic test. The other reader of the flag (the state watcher, under the connection's lock) and the `lost` signal were read again and have no such gap.
- **Why review and the tests missed it:** the delegate's argument for the epoch covered the answer path (check and ack in one critical section) and the order of the hooks; `IsOpen` was treated as two independent flags. - **U8, read in `amqp091-go` v1.17.0.** A connection has one reader goroutine (`Connection.reader`, `connection.go`). It reads frames in wire order and dispatches each one synchronously (`demux` → `dispatchN` → `Channel.recv` → `Channel.dispatch`, `channel.go`). For `basic.return`, `dispatch` sends the return to the `NotifyReturn` listeners; for `basic.ack` it calls the confirm sequencer, which resolves the deferred confirmation and sends to the `NotifyPublish` listeners. Both happen on that goroutine, and the next frame is not read before the current one is handed over. So if the broker writes the return before the ack, the application has the return before the confirm. Two conditions:
  1. The return listener must have room. `notifyAll` waits at most 5 s (`notifyTimeout`) for a full listener and then **drops** the notification. The relay's return channel therefore needs a capacity of at least one batch, or a goroutine that always drains it.
  2. The order on the wire is the broker's. RabbitMQ documents that it sends `basic.return` before `basic.ack`; the P1 test, repeated 100 times, checks it.
- **What later phases must take from the experiments** (inside the design; no decision needed):
  1. **Topology (P1).** Quorum queues are declared with `x-queue-type: quorum` and no priority argument; `x-max-priority` fails the declaration. `x-consumer-timeout` is sent as an `int64`: a Go `int` is encoded as 32 bits and wraps above 2³¹ − 1. Declaring an existing queue with another value of the argument, or without it, fails with 406, so changing the value later needs a policy or a new queue. RabbitMQ 4.4.1 refuses a transient, non-exclusive queue (error 541); the queues of ADR-0001 are durable or exclusive, so the design is not affected.
  2. **Relay after a reconnect (P1, P3).** Publish sequence numbers restart at 1. Confirmations that were outstanding when the connection dropped stay pending for the whole outage, resolve as not acknowledged at the reconnect, and `NotifyPublish` receives nothing for them; in the verification run all 62 such messages were in the queue. They are "unknown", not rejected: the row stays `pending`, is published again, and the claim guard drops the duplicate. A `Publish` during the outage returns `ErrClosed` at once.
  3. **Signals (P3).** The reconnect hook is the connection's `reconnecting → open`; giving up is `→ closed` with a non-nil `Err`. `NotifyClose` is not a reliable signal: it can receive extra errors during recovery, and it is closed without a value both when recovery gives up and on a normal `Close`. A channel's own state stays `open` during the outage.
  4. **Recorded topology (P1).** The library records declarations per channel and forgets them when the application closes that channel. Declaring on every (re)connection, as D2 requires, covers this.
  5. **Consumer timeout (P3).** After the broker's `basic.cancel`, acknowledging the held delivery returns nil and is ignored; the message is delivered again. The resubscribe safety net drops the deliveries of a cancelled consumer, and the claim guard covers one that was already being sent.
  6. **Requeue (P1).** A message returned with `nack` is delivered before higher-priority messages that are already waiting. This is the limitation D7 names, observed; ADR-0001 and `future-work.md` said the message goes behind others of its priority and were corrected.
  7. **API (P1, P2).** `http.ServeMux` answers an unknown path or method itself with `text/plain` (404, 405), and the generated wrapper's default error handler also writes `text/plain`: the mux is wrapped and `ErrorHandlerFunc`, `RequestErrorHandlerFunc` and `ResponseErrorHandlerFunc` are set. The generated code does not validate a body against the schema (`{}` is accepted where `name` is required); required fields are checked by the validation of ADR-0006 §5.
  8. **Provider client test (P1).** With `httptrace`, only the first `GotConn` says whether the pooled connection was used; a replay calls it again on a new connection.
  9. **Connection epoch (P3).** The epoch must have advanced before the first delivery of the recovered channel is stamped; otherwise a new delivery is taken for an old one, dropped without an ack and held unacknowledged by the broker. After a connection loss there is time (the first reconnection attempt waits 5 s). After a channel-only reopen there is not: E4 saw the library reopen a channel in about 3 ms. The state notification and the delivery arrive on different Go channels, so the implementation must not depend on which is read first.
