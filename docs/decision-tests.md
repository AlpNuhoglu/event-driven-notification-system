# Decision tests

For every decision of the [decision ledger](ai/decision-ledger.md) (`G1`–`G5`, `D1`–`D79`), in ledger order: the decision in a few words, the tests that would fail if the decision were not implemented, and, where a Go test cannot check it (documentation, process, repository settings), the evidence instead. This is the evidence behind the sentence of [ADR-0010](adr/0010-testing-and-ci.md) §1 "Every decision in the decision ledger has at least one test", and the list of the places where that sentence does not hold yet.

**How to read the table.**

- **Tests** names test functions under their package (the directory from the repository root). Build tags: tests in files ending in `_integration_test.go`, and every test in `internal/integration`, run with `-tags=integration` (`make test`); `test/e2e` runs with `-tags e2e` on the Compose stack (`make test-e2e`); `experiments/` are the first-hour experiments of P0, kept as the record of the behaviour the design rests on.
- **Covered** is strict: **yes** when removing the decided behaviour makes a named test fail; **partly** when part of the decision has no such test (the notes say which part); **no** when nothing would fail; **n/a** when the decision is not something a Go test can check (the notes name the evidence, or say "none").
- Several decisions fix a default value. `TestDefaultsMatchEnvExample` only keeps the code and `.env.example` together; `TestDefaults_AreTheLedgerValues` (`internal/platform/config`) keeps both at the value the ledger decided, so it is named for each of them.
- **The guard** `TestDecisionTests_NameRealTestsForEveryLedgerDecision` (`internal/testutil`, part of `make test`) fails when a decision of the ledger has no row here, when a row names a decision the ledger does not have, when the rows leave ledger order, or when a test named here does not exist in its package; `TestADR0010_NamesOnlyExistingTests` does the same for every test name in ADR-0010 (the actor-pair matrix, the tests by area, the mutation table). A name ending in `…` is a prefix that at least one test must match.

## The actor-pair matrix

Each of the 21 tests of the matrix in [ADR-0010](adr/0010-testing-and-ci.md) §1 was read in P6 to see whether it pits the two actors of its cell against each other on the same notification.

| Cell | Test | Verdict |
|---|---|---|
| api × api | `TestCancel_Idempotent` | Sequential: two cancels of one notification, the second answered from the state the first left. Two api calls on the same notification, but not a race. The race is now `TestCancel_ConcurrentSameNotification` (`internal/store`, added in P6): eight concurrent cancels of one pending notification, 25 rounds; exactly one applies and returns the event, the others are answered as a repeated cancel, and the version rises by one. (`TestCancelBatch_ConcurrentSameBatch` and `TestCancelBatch_ConcurrentHTTP` do the same for every row of a batch.) The matrix cell names both. |
| api × api | `TestIdempotencyKey_ConcurrentSameKey` | Yes. Two functions carry the name: `internal/api` (eight concurrent creates with one key through HTTP) and `internal/store` (the second create waits inside the first one's transaction). Both race two creates for the one notification the key creates. |
| api × relay | `TestCancel_DuringRelayPublish` | Yes. The cancel waits on the relay's lane transaction and applies to the committed `queued` row; the worker's claim then matches zero rows. |
| api × relay | `TestRedrive_VersusExpiry` | Yes, in its subtest "relay expiry pass and redrive concurrently" (20 rounds, the relay's expiry statement and the redrive started together); the other subtests check the redrive rules in sequence, mostly against the claim's expiry branch. |
| api × worker | `TestCancel_RacesWithClaim` | Yes: both orders, both waiting on a held lock in a known order, and 200 concurrent rounds in which both winners must occur. |
| api × lease sweeper | `TestCancel_WhileProcessingReturns409` | **No.** It cancels a `processing`, `sent` and `failed` row; there is no lease sweeper in it. The pair is now `TestCancel_VersusLeaseSweep` (`internal/store`, added in P6): a cancel before, during (the sweeper holding the row in its transaction) and after the sweep, and 100 concurrent rounds. It shows that a cancel never applies to a row the sweeper holds and does not wait for it: the row is `processing` in the cancel's snapshot, so the answer is `409`, and a cancel after the sweep applies with `may_have_been_sent`. The matrix cell names it now. |
| api × late worker | `TestLateSuccess_AfterCancel` | Yes (sequential, which is the nature of the pair): cancel after the sweep, then the late success; `cancelled → sent`. |
| api × late worker | `TestLateSuccess_AfterRedrive` | Yes: the late success applies to the redriven row, and not once the redriven row has been claimed again. |
| relay × relay | `TestRelay_TwoRelaysNeverPublishSameRow` | Yes: two relays with their own connections run their cycles at the same time on the same 180 rows; each row is published once. |
| relay × worker | `TestClaim_WaitsForRelayCommit` | Yes: the claim is started inside the lane transaction and seen waiting on the row lock. |
| relay × worker | `TestE2E_WorkerFasterThanRelayCommit` | Yes: the same race through the real broker, the relay's transaction held open until the claim is seen waiting. |

| relay × late worker | `TestLateSuccess_AfterReconcile` | Yes (sequential): swept, republished, reconciled to `pending`, then the late success applies. |
